# Sitemaps and search discovery

How the docs are discovered by **Google** and by our **own on-site search** (Algolia). The two
have different rules, and the most expensive mistakes in this area have all come from assuming
they are the same system. Companion to [`ROUTING-ARCHITECTURE.md`](./ROUTING-ARCHITECTURE.md)
(URL/edge routing) and [`VERSIONING.md`](./VERSIONING.md) (what gets built).

## TL;DR

- The build emits **one sitemap per served tree** — `/docs/<version>/<variant>/sitemap.xml` —
  regenerated on every deploy, so a sitemap can never drift from the tree it describes.
- **Google** follows a single index at **`/docs/sitemap.xml`**, which lists only the
  **indexed** trees (today `v2 × {union, flyte}`). One URL, referenced once from the
  marketing site's root `robots.txt`.
- **Algolia does not crawl the site.** Since 2026-08-13 the search index is built from the
  built output in `dist/` and pushed at deploy time by `make index-search`. It indexes **every**
  tree, including the `noindex` ones, because it never reads a `robots` meta tag. Sitemaps are
  for Google only. See [`tools/algolia_indexer/README.md`](./tools/algolia_indexer/README.md).
- **`noindex` does not mean "not searchable".** Keeping those two ideas separate is what
  prevents a repeat of the incident described below.
- **A file at the `/docs` root is invisible without a Cloudflare exclusion.** A catch-all
  redirect swallows the whole path space above Pages.
- **AI agents get the same treatment via `llms.txt`** — the marketing file holds one pointer
  to `/docs/llms.txt`, which regenerates per deploy. Same one-URL-handoff as the sitemap index.

## The six sitemaps

One per served tree. Counts verified live 2026-09-02 (they move with every cut, so treat them as
a shape rather than a fact to rely on):

| Sitemap | URLs | Indexed by Google | In the search index |
|---|---:|---|---|
| `/docs/v2/union/sitemap.xml` | 700 | **yes** | yes |
| `/docs/v2/flyte/sitemap.xml` | 579 | **yes** | yes |
| `/docs/v1/union/sitemap.xml` | 665 | no (DOC-1291) | yes |
| `/docs/v1/flyte/sitemap.xml` | 727 | no (DOC-1291) | yes |
| `/docs/latest/union/sitemap.xml` | 700 | no (bleeding edge) | yes |
| `/docs/latest/flyte/sitemap.xml` | 579 | no (bleeding edge) | yes |

Generated by `layouts/sitemap.xml` during each variant's Hugo build. Two properties worth
knowing:

- **`<loc>` is fully qualified.** The build runs with a path-only `baseURL`
  (`run_hugo.sh` passes `--baseURL /docs/<version>/<variant>/`), so `.Permalink` is a path.
  The sitemaps.org protocol requires absolute URLs, so the template prefixes the host via
  [`layouts/partials/site-host.html`](./layouts/partials/site-host.html), which derives it
  from the `docs_root` param. Do not "fix" this by making `baseURL` absolute — see the
  gotchas below.
- **Only pages this variant publishes are listed.** The template reuses
  `partials/page-allowed.html`, the same variant gate `baseof.html` uses. Hugo writes no
  file at all for a variant-excluded page, so listing one would hand crawlers a 404.

"Up to date" means **matches its own tree**, not "reflects newest content". Each tree builds
from its own ref, so `/docs/latest` moves on every merge while `/docs/v2` moves only at a
cut. The table above happens to show `latest` and `v2` level on both variants (700/579), because it
was read just after a cut. A gap in either direction is normal: `latest` runs ahead as pages
merge, and the gap closes at the next cut.

## Google: the sitemap index

### What exists

`build_versions.sh` writes **`/docs/sitemap.xml`**, a `<sitemapindex>` listing the sitemaps of
the trees it built **indexed**:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap><loc>https://www.union.ai/docs/v2/flyte/sitemap.xml</loc></sitemap>
  <sitemap><loc>https://www.union.ai/docs/v2/union/sitemap.xml</loc></sitemap>
</sitemapindex>
```

Driven by `INDEXED_LABELS`, accumulated by `build_version()` from what was actually built, so
the index cannot advertise a tree this run did not produce.

### Why an index rather than naming the sitemaps directly

The marketing site adds **one line, once**, and which trees sit behind that URL stays ours to
change. Handing them the per-variant sitemaps would put a ticket on another team at every
cut, new variant, or line retirement. That standing coupling is exactly what left their
hand-maintained docs list 94% stale.

### Why only indexed trees

Advertising a `noindex` page in a sitemap is what makes Search Console report
**"Submitted URL marked 'noindex'"**. Listing `latest`, the pins, or v1 would manufacture
thousands of errors for pages we deliberately withhold.

### Who writes it

**Only the line that owns `/docs/latest`** — the primary line, which also emits the top-level
`/docs` landing pages. The two lines deploy separately, so a shared file at the `/docs` root
needs exactly one writer or the deploys race. Same constraint that made the version manifests
per-line rather than shared (DOC-1330).

**Consequence:** the index can only list trees *that line* built. If a secondary line is ever
made indexable, adding it here is a deliberate change, not an automatic one.

### Required: a Cloudflare exclusion (applied 2026-08-11)

**A file at the `/docs` root is not reachable without one.** The **F3: docs-root fallback**
redirect rule sweeps the `/docs/*` path space to the v2 user guide, and it runs at the CDN
**above** Pages, so the origin file is never consulted. Measured before the fix:

```
/docs/sitemap.xml          302 -> /docs/v2/union/user-guide/
/docs/zzz-nonexistent.xml  302 -> /docs/v2/union/user-guide/   (same rule)
/docs/index.html           302 -> /docs/v2/union/user-guide/   (a real built file)
/docs/v2/versions.json     200                                 (explicitly excluded)
```

`versions.json` returns 200 only because DOC-1330 added an exclusion for it; `/docs/llms.txt`
likewise from DOC-1358. `/docs/sitemap.xml` now has the same clause, added to F3 in the
`union.ai` zone's dynamic-redirect ruleset (v62 -> v63):

```
and not (http.request.uri.path eq "/docs/sitemap.xml")
```

Verified live: `/docs/sitemap.xml` now returns **200 `application/xml`** with the index.
Immediately after the rule change and before the build shipped a file there it returned **404**,
which was the correct intermediate state — the request reaching Pages and finding nothing is the
proof the exclusion works. `/docs/zzz-unknown.xml` still redirects, confirming the exclusion is
exact rather than a blanket `.xml` passthrough.

**Any future file added at the `/docs` root needs its own clause.** There are now three
(`versions.json`, `llms.txt`, `sitemap.xml`); the pattern is one `and not (... eq "<path>")`
per file.

> **Trap: the PR preview cannot detect this.** Previews are served from
> `*.docs-dog.pages.dev`, where the `www.union.ai` zone rules do not apply. The index will
> work perfectly on a preview and be invisible in production. Verify this one **on
> production after deploy**, or against the zone — never on the preview alone.

### The root robots.txt (live since 2026-08-11)

`https://www.union.ai/robots.txt` is **marketing-owned** (the corporate site is served by
Webflow) and now declares both sitemaps:

```
Sitemap: https://www.union.ai/sitemap.xml
Sitemap: https://www.union.ai/docs/sitemap.xml
```

That second line is the whole connection between Google and the docs. It is one line, added
once, and never needs touching again — which trees sit behind it is ours to change.

`/docs/sitemap.xml` is also submitted directly in **Google Search Console** (property
`union.ai`, submitted 2026-08-11, classified as a *Sitemap index*). That is an independent
channel: it works whether or not the root `robots.txt` is ever re-read, and is usually faster.

**The marketing sitemap is auto-generated too.** `www.union.ai/sitemap.xml` was a
hand-maintained list that had drifted to 987 URLs, 781 of them stale `/docs/` entries and 94%
of those dead. It is now generated by Webflow on publish (212 URLs, marketing pages only, zero
docs URLs), with **Use global canonical tag URL as domain** enabled — required, because the
site publishes to `web.union.ai` while every page canonicals to `https://www.union.ai`, so
without it the generated sitemap would advertise 212 non-canonical hostnames. Net effect: the
two sitemaps have an exact ownership split, zero overlap, and neither is hand-curated.

**The `robots.txt` this build emits governs nothing.** It lands at
`/docs/<version>/<variant>/robots.txt`, and crawlers only read `robots.txt` at the **host
root**. That includes its `Disallow: /*.md$` directive, which has never had any effect.
The file is kept valid and copy-pasteable, not operative.

Why `robots.txt` rather than having marketing's `sitemap.xml` point at ours: **sitemap indexes
cannot nest.** The protocol forbids a sitemap index listing another sitemap index, so their
index cannot reference ours. The only alternative would be listing our per-variant sitemaps
directly, which reinstates the coupling the index exists to remove.

Google Search Console submission is an independent third channel — it works whether or not
the root `robots.txt` is ever updated, and is usually faster.

## LLM and agent discovery: llms.txt

The same shape as the sitemaps, for a different consumer. [llmstxt.org](https://llmstxt.org/)
defines `llms.txt` at the domain root as the file an AI agent or AI search engine looks for.

```
www.union.ai/llms.txt          marketing-owned, hand-curated, UPLOAD-only
  └─ /docs/llms.txt            ours, regenerated on every docs deploy
       ├─ /docs/v2/llms.txt    current
       └─ /docs/v1/llms.txt    legacy
```

`/docs/llms.txt` is the root-lifted index (DOC-1358). It carries an explicit instruction to
prefer v2, then fans out to the per-line files. Like `/docs/sitemap.xml` it sits at the `/docs`
root, so **it needs its own Cloudflare exclusion** — see the section above; it already has one.

**The marketing file holds exactly one pointer to us, deliberately.** The Webflow control is an
**Upload**, not a generator, so anything written there is hand-maintained and rots. Enumerating
docs structure in it would recreate the 781-stale-URL problem the sitemap work just removed.
One link to `/docs/llms.txt` covers everything and survives version changes, because what sits
behind that URL regenerates on every deploy.

**Do not "improve" it by listing docs pages there.** That is the same mistake in a new file.

Two asymmetries worth knowing, because they cut against the sitemap intuitions above:

- **Curation is correct here.** `llms.txt` convention favours a concise index of useful entry
  points over exhaustiveness. The marketing file is 49 lines drawn from 212 live pages, and
  auto-generating all 212 would produce a *worse* artifact — the opposite of the sitemap, where
  completeness is the goal. See DOC-1409.
- **Nothing catches rot in it.** Webflow offers no auto-generate for `llms.txt`. When the file
  was audited on 2026-08-11, three of its links were stale — one 404 and two renamed pages —
  none of which anything had flagged. DOC-1409 proposes a link checker rather than a generator,
  for exactly this reason.

`llms.txt` is an emerging convention with far less crawler adoption than sitemaps. Worth one
line and a periodic check; not worth a standing maintenance commitment.

## Algolia: on-site search

### Index shape

One shared index (`union`), faceted by **`version × variant`**, where both come from the URL:

```js
const match = url.pathname.match(/^\/docs\/([^/]+)\/([^/]+)/);
```

The search widget ([`layouts/partials/search.html`](./layouts/partials/search.html)) reads the
same two segments from `window.location` and filters on them, so a reader only ever searches
the surface they are on.

### The hosted Crawler is retired — the index is built from `dist/`

> **This section used to describe a hosted Algolia Crawler. That is no longer how the served
> index is produced.** Since the 2026-08-13 cutover the index is built at deploy time from the
> built site and pushed by `make index-search`, which runs in `build-and-deploy.yml` after a
> successful production deploy. The mechanism, its record shapes and the reasoning are
> documented in [`tools/algolia_indexer/README.md`](./tools/algolia_indexer/README.md), which
> is the authority. Do not tune a crawler; there isn't one feeding the served index.

What this changes for the rest of this document:

- **`noindex` and site-search membership are now independent knobs.** Under the Crawler they
  were the same knob, because the Crawler obeyed `noindex`, and making v1 `noindex` for Google
  nearly deleted v1's 48,706 records, 56% of the index. It was caught only by a crawl safety
  check. That failure mode is gone by construction: the indexer reads `dist/`, so it never sees
  a `robots` meta tag.
- **Index membership follows the build, not a seed list.** Whatever exists at
  `dist/docs/<version>/<variant>/**/<path>.md` is indexed. There is no `sitemaps` seed,
  no `startUrls`, no `exclusionPatterns` and no `renderJavaScript` setting to keep in step.
  Served implies searchable; a tree that is not built produces no records.
- **Pins are handled by granularity, not exclusion**: current surfaces are indexed at full
  anchor granularity and pinned trees at page level, so a pin does not multiply the record
  count. See the indexer README.

**Check which Algolia application you are looking at before trusting any evidence.** The site
queries application `42EK9RXSGL`. The retired Crawler wrote to a **different** application,
`ZK72K15QRI`, which still exists and still answers queries with stale records. A query against
the retired app looks exactly like a query against the live one.

### Keeping the widget and the index in step

The widget's set of searchable versions is derived from the **version menu** — badged entries
(LATEST/STABLE) are the built-and-indexed trees, bare numbers are pins — rather than a second
hardcoded list. A pin falls back to its line's stable; an unknown segment drops the version
filter instead of matching zero records and showing an empty box.

Because index membership now follows the build, that derivation and the index agree by
construction: both are functions of what was built.

## Gotchas

- **Do not make `baseURL` absolute to fix `<loc>`.** `layouts/_default/single.md` and
  `list.md` already emit `https://www.union.ai{{ .Permalink }}` into the `<path>.md`
  outputs, so they would double-prefix; and previews and `make serve` would emit production
  URLs from every `.Permalink` consumer, making a preview impossible to check against itself.
  Prefix at the template via `site-host.html` instead.
- **Sitemap indexes cannot nest.** Relevant whenever someone proposes chaining ours off
  another index.
- **A sitemap must not list `noindex` pages.** Search Console reports them as errors.
- **A file at the `/docs` root needs a Cloudflare exclusion**, and the PR preview cannot
  detect its absence. See above.
- **The emitted `/docs/**/robots.txt` governs nothing.** Only the host-root file does.
- **`noindex` is not "unsearchable".** It is a directive to external engines. Our own index is
  built from `dist/` and does not read it, so a `noindex` tree stays searchable on-site.
- **The version selector is JS-only**, so no non-JS crawler can traverse between version
  trees. Sitemaps are the only inter-tree discovery path Google has. Our own index does not
  need one, because it reads the build directly.
- **`<lastmod>` in the index is deliberately omitted** — clock-derived output would make two
  builds of identical content differ, which `check-determinism` asserts against.

## Changing things

**Add a variant** — no action, for either consumer. The sitemap index enumerates
`INDEXED_LABELS × VARIANTS` and lists only sitemaps that exist on disk, and the search index is
built from whatever the build produced.

**Make a line indexable** — set `indexed` in that line's `versions.toml`. Its stable tree then
builds indexed and joins the sitemap index *if the primary line builds it*; otherwise the
index needs a deliberate change (see "Who writes it").

**Withhold a line from Google** — the inverse, and safe for on-site search. `noindex` affects
external engines only; the search index is built from `dist/` and never reads the meta tag, so a
noindexed line stays fully searchable on the site. This is the one thing the Crawler got wrong.

**Retire a tree** — it drops out of the index automatically, since the index is generated from
what was built.
